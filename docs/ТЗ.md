# ТЗ v3. «ШТАБ» — веб-платформа координации наблюдателей

**Версия:** 3.0 (полная, отменяет v2)
**Дата:** 29 августа 2026
**Целевое событие:** выборы депутатов Государственной Думы IX созыва, голосование 18–20 сентября 2026
**Формат:** PWA (устанавливаемое веб-приложение) + полноценная десктопная версия
**Исполнение:** малая команда + Claude Code

---

## 1. Что изменилось относительно v2 и почему

| Решение v2 | Решение v3 | Обоснование |
|---|---|---|
| Telegram Mini App | **PWA на собственном домене** | Зависимость от одного мессенджера — единая точка отказа. PWA ставится на рабочий стол в один шаг, работает на Android, iOS и ПК из одного кода |
| Только мобильный сценарий | **Мобильная + десктопная версия из одной кодовой базы** | Штаб работает с большого экрана, наблюдатель — с телефона. Адаптив, а не два продукта |
| Свободная регистрация | **Учётные записи выдаются сверху** | Роль выбирает не пользователь. Иначе в штабной контур попадёт кто угодно |
| Плоская привязка «наблюдатель → УИК» | **Дерево: Федерация → Регион → ТИК → УИК** | Это реальная структура избирательной системы и структура штаба. Все права и все чаты выводятся из дерева |
| Чатов нет, только инциденты | **Иерархические чаты + треды инцидентов** | Живое общение всё равно будет. Лучше внутри системы, где есть контекст и история, чем в общем чате на 300 человек |
| Уведомления только по инцидентам | **Полноценный центр уведомлений и рассылок** | Штабу нужен канал «сказать всем сразу» с подтверждением прочтения |
| Карта упомянута | **Карта как отдельный модуль с данными и геокодированием** | Данные по участкам сами не появятся, это отдельная работа |
| Дашборд только для штаба | **Дашборд для каждой роли** | Наблюдатель, который видит общую картину, чувствует себя частью дела и не выпадает из процесса |

## 2. Контекст и жёсткие ограничения

- Голосование **18, 19, 20 сентября 2026**, участки открыты с 8:00 до 20:00 по местному времени, подсчёт вечером 20-го.
- ДЭГ проводится в 33 регионах — в MVP только приём обращений с тегом «ДЭГ».
- В стране около 94 тыс. участков. Пилот — один регион, 200–500 участков. Архитектура не должна ломаться при росте в 100 раз, но оптимизировать под 94 тыс. сейчас не нужно.
- 11 часовых поясов. В БД всё в UTC, отображение — в локальном времени узла.
- Связь на участках плохая, возможны ограничения мобильного интернета. **Офлайн-режим обязателен.**
- Времени на разработку меньше трёх недель, из них последняя неделя — обучение людей.

## 3. Принципы

1. **Роль и место определяются сверху.** Пользователь не может сменить себе ни то, ни другое.
2. **Видимость = поддерево.** Пользователь видит свой узел и всё, что под ним. Ничего сбоку и ничего сверху.
3. **Offline-first.** Приложение открывается и работает без сети. Синхронизация — фоном.
4. **Одна рука, тридцать секунд.** Основной сценарий — не больше четырёх нажатий.
5. **Фиксируем, а не обвиняем.** Никаких автоматических выводов о нарушениях.
6. **Ссылка на норму или ничего.** Правовой ответ всегда с источником.
7. **Минимум персональных данных.** Не собираем ничего, без чего система работает.

## 4. Организационная структура и роли

### 4.1 Дерево мест (org_node)

```
Федерация
└── Регион (субъект РФ)
    ├── Штаб региона                 ← узел типа «штаб»
    └── ТИК (территориальная комиссия)
        ├── Штаб ТИК / куст
        └── УИК (участковая комиссия)
```

Тип узла: `federation | region | hq | tik | uik`.
Путь хранится как `ltree`: `ru.r77.t012.u1234`. Проверка доступа — одно сравнение `path <@ scope`.

Узел «штаб» — это не географическая единица, а рабочая группа при регионе или ТИК. Юристы, диспетчеры и пресс-служба живут в штабных узлах.

### 4.2 Роли

| Код | Роль | Узел привязки | Область видимости |
|---|---|---|---|
| `observer` | Наблюдатель | УИК | свой УИК |
| `uik_senior` | Старший по участку | УИК | свой УИК + все наблюдатели участка |
| `mobile` | Мобильная группа / выездной юрист | ТИК | назначенные УИК |
| `coordinator` | Координатор куста | ТИК | все УИК под своим ТИК |
| `lawyer` | Юрист штаба | Штаб региона | инциденты со статусом «нужен юрист» в регионе |
| `dispatcher` | Диспетчер ситуационного центра | Штаб региона | весь регион |
| `region_head` | Руководитель штаба региона | Штаб региона | весь регион, включая ПДн своих людей |
| `federal` | Федеральный штаб | Федерация | вся страна, агрегаты + детали по запросу |
| `press` | Пресс-служба | Штаб | только агрегаты и одобренные материалы |
| `admin` | Администратор | Федерация | всё + управление пользователями и аудит |

### 4.3 Матрица прав (ключевое)

| Действие | observer | uik_senior | coordinator | lawyer | dispatcher | region_head | admin |
|---|---|---|---|---|---|---|---|
| Создать инцидент | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ |
| Видеть чужие инциденты | ❌ | своего УИК | своего куста | назначенные | регион | регион | все |
| Менять статус инцидента | только «решено у меня» | ✅ своего УИК | ✅ | ✅ | ✅ | ✅ | ✅ |
| Назначать исполнителя | ❌ | ❌ | ✅ | ❌ | ✅ | ✅ | ✅ |
| Писать в чат ТИК | ❌ | ❌ | ✅ | ✅ | ✅ | ✅ | ✅ |
| Рассылка уведомлений | ❌ | ❌ | по своему кусту | ❌ | по региону | по региону | везде |
| Создавать пользователей | ❌ | ❌ | по своему кусту | ❌ | ❌ | по региону | везде |
| Видеть телефоны людей | ❌ | своего УИК | своего куста | ❌ | регион | регион | все |
| Публиковать наружу | ❌ | ❌ | ❌ | ❌ | ❌ | заявка | ✅ |

Правило, которое нельзя нарушать: **пользователь не может выдать роль выше собственной и не может выдать доступ вне своего поддерева.** Проверять на сервере, не на клиенте.

## 5. Регистрация, вход и доступ

### 5.1 Модель: учётные записи выдаются, а не создаются

Самостоятельной регистрации нет. Это единственный надёжный способ не пустить посторонних в штабной контур.

**Сценарий А — массовый импорт (основной).**
Координатор загружает CSV: `фамилия;имя;телефон;роль;узел`. Система:
1. Валидирует телефоны и номера УИК, показывает предпросмотр с ошибками.
2. Создаёт учётные записи, генерирует пароли (6 слов или 8 символов, читаемые, без похожих знаков: `bez-lishnih-7`).
3. Формирует файл для раздачи и/или отправляет SMS с логином, паролем и ссылкой.
4. При первом входе — обязательная смена пароля и согласие на обработку персональных данных.

**Сценарий Б — код приглашения (резервный).**
Координатор генерирует одноразовый код, привязанный к роли и узлу, со сроком жизни 72 часа. Человек вводит код, телефон, подтверждает SMS-кодом, задаёт пароль. Роль и узел приходят из кода — выбрать их вручную нельзя.

**Чего не делаем:** свободной формы «выберите свою роль», регистрации по e-mail, входа через соцсети.

### 5.2 Вход
Логин — номер телефона в формате `+7XXXXXXXXXX` (нормализация на входе), пароль. Опционально код из SMS как второй фактор — **обязателен для ролей `dispatcher`, `region_head`, `admin`**.

Сессии: JWT access 15 минут + refresh 30 дней с ротацией. Refresh привязан к устройству, список устройств виден пользователю и администратору. Пять неудачных попыток — блокировка на 15 минут, десять — уведомление координатору.

### 5.3 Восстановление доступа
Не через e-mail. Два пути: SMS-код на тот же номер, или сброс координатором в панели (человек звонит своему координатору). В день голосования второй путь основной — SMS может не дойти.

### 5.4 Жизненный цикл
`создан → приглашён → активен → приостановлен → архивирован`. Отключение мгновенно закрывает все сессии. Все изменения роли и узла пишутся в неизменяемый аудит-лог.

## 6. Функциональные модули

### 6.1 Пульт и чек-ины

Главный экран наблюдателя: номер УИК, текущая фаза дня, четыре крупные кнопки — **Всё в порядке / Есть вопрос / Нарушение / SOS**. Ниже — кнопка чек-ина и счётчик неотправленных событий.

Чек-ин раз в 60–90 минут одной кнопкой, по напоминанию. Состояния участка: 🟢 <90 мин, 🟡 90–150 мин, 🔴 >150 мин, ⚪ нет данных. Никакого фонового геотрекинга; координаты берутся только в момент создания инцидента и только с явного согласия.

### 6.2 Инциденты

Обязательные поля: узел, категория, время, короткое описание. Опционально: медиа, свидетели, что уже предпринято.

Каждое вложение получает SHA-256, время устройства, время сервера, автора. Хеши пишутся в append-only журнал.

Статусы: `новый → принят → в работе → нужен юрист → жалоба подана → решён | отклонён | без последствий`.

Приоритеты и целевое время реакции:

| Категория | Приоритет | Реакция |
|---|---|---|
| Удаление наблюдателя, давление, угрозы | P0 | 3 мин + звонок |
| Расхождение номеров сейф-пакетов и пломб | P0 | 5 мин |
| Вброс, подвоз, организованное голосование | P0 | 5 мин |
| Недопуск к документам, к столу выдачи | P1 | 15 мин |
| Нарушения при подсчёте и в протоколе | P1 | 15 мин |
| Агитация, вопросы по КОИБ | P2 | 60 мин |
| Организационное, техника | P3 | по возможности |

Каждый инцидент автоматически создаёт **тред-чат** (см. 6.5) с участниками: автор, владелец, юрист при эскалации.

### 6.3 Чек-листы фаз и сейф-пакеты

Семь фаз трёхдневки: подготовка → открытие 18-го → день → закрытие дня → открытие следующего дня → подсчёт → протокол. На каждой фазе — короткий чек-лист с тумблерами «да / нет / спорно»; «нет» и «спорно» автоматически создают инцидент с предзаполненным описанием.

Сейф-пакеты: вечером фиксируются номера пломб и фото; утром система показывает вчерашние номера и просит подтвердить. Расхождение — P0 и готовый проект жалобы. Дополнительно сверяется число проголосовавших на конец дня и на начало следующего.

### 6.4 Явка и протокол

Явка вводится в контрольные часы (10:00 / 12:00 / 15:00 / 18:00 / 20:00 местного), с напоминанием. Аномалии не помечаются как нарушения — только как «уточнить у наблюдателя».

Протокол: фото → распознавание чисел → **обязательная ручная проверка человеком** → автопроверка контрольных соотношений (набор выносится в конфиг, а не в код) → предупреждение о несходящихся строках до подписания. Отдельный флаг «заверенная копия получена» и фото копии.

### 6.5 Чаты по иерархии

Общего чата на всех нет и не будет — это главная причина, по которой в день голосования теряются сообщения.

**Типы каналов (создаются автоматически при создании узла):**

| Канал | Участники | Назначение |
|---|---|---|
| `uik:{id}` | наблюдатели участка, старший, координатор куста | всё по своему участку |
| `tik:{id}` | координаторы кустов, штаб ТИК, юрист | координация района |
| `region:{id}` | координаторы ТИК, диспетчеры, юристы, руководитель | управление регионом |
| `role:lawyers@{region}` | юристы региона | профессиональный обмен |
| `incident:{id}` | автор, владелец, привлечённые | тред по конкретному инциденту |
| `announce:{node}` | все под узлом | только чтение, объявления штаба |

**Правила доступа:**
- Пользователь видит каналы своего узла и всех узлов вверх по ветке, где ему явно дан доступ.
- Наблюдатель не может писать в канал чужого УИК и не видит его существования.
- Личные сообщения возможны только по вертикали: наблюдатель ↔ свой координатор, координатор ↔ штаб. Горизонтальных личных переписок между незнакомыми людьми нет — это защита от социальной инженерии.
- Координатор и выше могут удалить сообщение; удаление логируется, текст сохраняется в аудите.

**Функции:** текст, фото со сжатием, **голосовые сообщения** (на участке это быстрее набора), цитирование, реакции, кнопка «превратить сообщение в инцидент», пометка «срочно» (даёт звук у получателей), поиск по истории, экспорт переписки в отчёт по участку.

**Техника:** WebSocket через Redis pub/sub, при обрыве — long-poll каждые 10 секунд, история подгружается страницами, непрочитанные считаются на сервере. Сообщения, написанные офлайн, ставятся в ту же очередь, что и инциденты, и помечаются часами отправки, а не получения.

### 6.6 Уведомления и рассылки

**Типы:** `broadcast` (объявление штаба), `targeted` (по роли и узлу), `personal` (ответ по инциденту, назначение), `system` (напоминание о чек-ине, о вводе явки, о фазе).

**Приоритеты:**
- `info` — значок в приложении;
- `important` — push + звук;
- `critical` — push + звук + **обязательное подтверждение прочтения**; если через 10 минут не подтверждено, уходит SMS, ещё через 10 — задача координатору позвонить.

**Панель рассылки:** выбор аудитории (узел + роли + фильтр «только активные / только без связи»), предпросмотр количества получателей, приоритет, шаблоны. Отправка требует подтверждения и пишется в аудит с указанием автора. Обязательный лимит: не более N рассылок в час, чтобы люди не начали игнорировать уведомления.

**Каналы доставки:** внутри приложения (WebSocket) → Web Push (VAPID) → SMS для `critical`.

**Честное ограничение:** на iOS web push работает только если приложение добавлено на домашний экран (iOS 16.4+). Поэтому шаг «добавить на экран» — обязательная часть онбординга с картинками, а SMS-канал для критических сообщений обязателен, а не опционален.

### 6.7 База знаний

Структура: разделы → статьи → карточки быстрых ответов. Каждая статья: краткий ответ, «что делать», основание (норма или пункт методички), дата актуализации, автор-юрист.

Обязательные разделы: права наблюдателя, открытие участка, день голосования, ночное хранение, надомное голосование, КОИБ, подсчёт, протокол, жалобы, что делать при удалении с участка, ДЭГ, контакты.

Поиск: полнотекстовый по-русски (Postgres `ru` конфигурация + триграммы для опечаток). **Вся база кэшируется офлайн** при первом входе — это важнее всех остальных офлайн-функций.

Версионирование: правки видны, у каждой статьи есть история. Публиковать может только юрист или администратор.

### 6.8 ИИ-помощник

Работает **поверх базы знаний**, а не вместо неё. Конвейер: вопрос → гибридный поиск (полнотекст + векторный) → топ-6 фрагментов → если релевантность ниже порога, честное «не знаю» и кнопка «позвать юриста» → иначе генерация строго по фрагментам → проверка, что в ответе есть ссылка на реальный источник из выдачи.

Формат ответа: короткий ответ 1–2 предложения, «что сделать сейчас» 2–4 пункта, «основание» свёрнуто, кнопки «Помогло» / «Позвать юриста» / «Оформить жалобу».

Ограничители: не выдумывать номера статей; не давать оценок законности выборов; не подталкивать к конфликту с комиссией; ограничение ответа 60–90 слов.

Модель: GigaChat или YandexGPT (данные остаются в России). Провайдер спрятан за интерфейс `LLMProvider` — замена в один файл. Эмбеддинги — локальная многоязычная модель на CPU, корпус маленький.

**Блокирующий критерий приёмки:** набор из 100 вопросов, проверенных юристом; ноль выдуманных ссылок на нормы; не менее 90% честных «не знаю» на вопросах вне корпуса.

Офлайн: топ-100 карточек кэшируются, помощник отвечает по кэшу с честной пометкой.

### 6.9 Карта

**Данные.** Это отдельная работа, и её надо начать в первый день:
1. Выгрузить перечень УИК пилотного региона (номер, адрес, привязка к ТИК) из открытых источников избирательной комиссии.
2. Пакетно геокодировать адреса. Ручная проверка выборочно и обязательная — для всех участков, где геокодер не уверен.
3. Хранить `geocode_quality`: `точно | приблизительно | центроид ТИК | нет`. На карте участки с неточными координатами показывать иначе, чтобы штаб не принимал решения по кривым данным.

**Отображение.** MapLibre GL JS, тайлы OpenStreetMap (или собственный тайл-сервер, если нужна независимость от внешнего провайдера). Кластеризация — supercluster. При большом числе точек — серверная агрегация по зуму, а не 94 тысячи маркеров в браузере.

**Слои (переключаемые):**
- статус участков 🟢🟡🔴⚪;
- открытые инциденты (размер маркера = приоритет);
- покрытие наблюдателями (есть человек / нет человека) — самый полезный слой до дня Д;
- явка по ТИК заливкой;
- протоколы получены / не получены (вечер 20-го).

**Карточка участка при клике:** номер, адрес, наблюдатель (по правам), статус, последний чек-ин, явка, число инцидентов, кнопки «открыть чат участка» и «позвонить».

**Приватность:** в публичном контуре карта показывает только агрегаты по ТИК. Фамилии наблюдателей и привязка «человек ↔ участок» наружу не выходят никогда.

**Офлайн:** карта — единственный модуль, который офлайн не работает. Деградация на список участков с фильтрами.

### 6.10 Дашборды и инфографика

Дашборд свой у каждой роли — это и есть «сводка для всех».

**Наблюдатель:** мой участок (фаза, чек-ин, мои инциденты), плюс агрегаты по ТИК, региону и стране: сколько участков под наблюдением, сколько обращений принято, сколько решено. Человек должен видеть, что он часть большого процесса.

**Координатор:** таблица своих УИК со светофором, кто без связи, кто не ввёл явку, открытые инциденты куста.

**Диспетчер:** очередь инцидентов по приоритету с таймером просрочки, карта, счётчики, кнопка «позвонить» в один клик.

**Руководитель штаба:** шесть цифр сверху (участков под наблюдением / активных сейчас / без связи >2ч / открытых инцидентов / P0 / протоколов получено), графики явки, воронка инцидентов, среднее время реакции, выгрузки.

**Пресс-служба:** только одобренные агрегаты + генератор карточек.

**Графики:** линия явки по часам, воронка статусов инцидентов, распределение по категориям, гистограмма времени реакции, покрытие участков во времени. Библиотека — Recharts.

**Генератор карточек:** серверный рендер PNG 1080×1080 и 1080×1920 по шаблону с фирменными цветами. Текст вида «за первые шесть часов: 1 284 участка, 37 обращений, 31 решено на месте, среднее время ответа 4 минуты». Реализация — HTML-шаблон → скриншот через headless-браузер, либо satori/resvg. Это дешёвая функция с очень высокой видимостью для партии.

**Публичный «Пульс»** (отдельная страница без авторизации, включается флагом): только агрегаты, только подтверждённые данные, кэш 60 секунд, никаких формулировок о нарушениях до правовой квалификации.

### 6.11 Администрирование

Пользователи (создание, импорт, сброс пароля, блокировка, история ролей), справочники (узлы, категории инцидентов, шаблоны жалоб, контрольные соотношения, шаблоны рассылок), аудит-лог с поиском, фиче-флаги (включить/выключить модуль без выкладки), статус системы (очереди, задержки, ошибки).

## 10. Архитектура и стек

```
PWA (React 18 + TypeScript + Vite)
 ├── Tailwind + shadcn/ui        интерфейс
 ├── TanStack Query              данные и кэш
 ├── Dexie (IndexedDB)           офлайн-очередь и кэш базы знаний
 ├── Workbox                     service worker, precache, background sync
 ├── MapLibre GL + supercluster  карта
 └── Recharts                    графики
        │ HTTPS + WSS
API (FastAPI, Python 3.12, SQLAlchemy 2, Pydantic v2)
 ├── PostgreSQL 16 (+ PostGIS, ltree, pg_trgm, pgvector)
 ├── Redis (pub/sub, кэш, очереди, rate limit)
 ├── S3-совместимое хранилище (медиа)
 ├── worker (ARQ): OCR, PDF, рендер карточек, рассылки, SMS
 └── LLM-сервис: RAG + провайдер модели

Инфраструктура: Docker Compose, Caddy (TLS), российский хостинг,
мониторинг (Sentry/GlitchTip + Uptime Kuma), ежечасные бэкапы БД
```

**PWA-специфика:**
- `manifest.json`: `display: standalone`, иконки 192/512, `theme_color`, `start_url` со счётчиком установки.
- Service worker: app shell в precache, API GET — stale-while-revalidate, POST — очередь через Background Sync (Android) и повтор при открытии (iOS).
- Обновления: `skipWaiting` + баннер «доступна новая версия, обновить».
- Онбординг установки: отдельный экран с инструкцией для Android (Chrome → «Установить приложение») и iOS (Safari → «Поделиться» → «На экран Домой»). Без этого шага на iPhone не будет push-уведомлений.

**Про устойчивость доступа.** Приложение живёт на собственном домене, поэтому не зависит ни от одного мессенджера. Разумные меры на случай проблем с доступом: короткий основной домен + резервный поддомен, адрес продублирован в памятке на бумаге, критические уведомления дублируются по SMS, и у каждого наблюдателя есть телефон координатора. Это обычная практика надёжности, а не что-то экзотическое.

## 11. Связь и деградация

1. **Есть сеть** — всё работает, реальное время через WebSocket.
2. **Плохая сеть** — очередь в IndexedDB, фото сжимаются до 1600 px, видео вручную, WebSocket падает в long-poll.
3. **Нет сети** — работают: пульт, создание инцидентов, чек-листы, база знаний, кэш помощника, черновики сообщений. Не работают: карта, дашборд, живой чат.
4. **Совсем нет интернета** — SMS на короткий номер по шаблону `SOS 1234 P0 недопуск` и звонок координатору. Такие обращения попадают в общую очередь с пометкой «через SMS».

На экране всегда виден счётчик неотправленного. Человек должен понимать, дошло сообщение или нет.

## 12. Безопасность и персональные данные

**Не собираем и технически блокируем:** фотографии списков избирателей и любых страниц с ФИО граждан, паспортные данные избирателей. При выборе категории «проблемы со списками» — предупреждение до открытия камеры.

**Собираем минимум:** ФИО, телефон, узел, роль. Телефон шифруется в БД, в логах маскируется.

**Меры:** argon2id для паролей, обязательный второй фактор для штабных ролей, полный аудит действий, rate limiting, размещение данных на серверах в России, ретенция медиа 12 месяцев, регулярные бэкапы с проверкой восстановления.

**Отдельно:** система хранит утверждения о нарушениях, то есть сведения о конкретных людях. До правовой квалификации это версии, а не факты. Публичный контур не связывает формулировки о нарушениях с конкретными фамилиями и номерами участков.

## 14. План на 20 дней

Команда-минимум: 1 фулстек + 1 фронтендер + вы (продукт, данные, обучение) + юрист партии на 10 часов + координатор пилотного региона.

| Дни | Работа | Результат |
|---|---|---|
| 1–2 | Каркас, БД, дерево узлов, вход по телефону, импорт пользователей | Люди могут войти |
| 3–4 | Инциденты, медиа, офлайн-очередь, очередь диспетчера | Сквозной сценарий |
| 5–6 | Чаты по иерархии, WebSocket, треды инцидентов | Общение внутри системы |
| 7 | PWA: манифест, service worker, установка на экран, push | Ставится на телефон |
| 8 | Уведомления и рассылки, SMS-канал | Штаб может достучаться до всех |
| 9 | База знаний + офлайн-кэш; параллельно юрист пишет карточки | Справочник работает |
| 10 | **Пилот на 20–30 людях**, живая тренировка | Список из 40 багов |
| 11 | Правки по пилоту | Стабильность |
| 12 | Карта: данные УИК, геокодирование, слои | Карта региона |
| 13 | Дашборды по ролям, графики | Сводка для всех |
| 14 | ИИ-помощник + eval-набор на 100 вопросов | Помощник не врёт |
| 15 | Сейф-пакеты, чек-листы фаз, шаблоны жалоб | Трёхдневка закрыта |
| 16 | Протокол и контрольные соотношения, генератор карточек | Полный набор |
| 17 | Нагрузка, мониторинг, бэкапы, резервные каналы | Не упадём |
| **18** | **Code freeze.** Обучение: видео 3 минуты, памятка А4 | Люди умеют пользоваться |
| 19–21 | Дни голосования, дежурство 24/7 | Работа |
| 22–24 | Отчёты, разбор, документ для партии | Материал для решения |

**Режем при отставании в этом порядке:** генератор карточек → протокол → карта → ИИ-помощник → сейф-пакеты.
**Не режем никогда:** вход и роли, инциденты, офлайн, чаты, уведомления, база знаний.

## 15. Риски

| Риск | Что делаем |
|---|---|
| Не успеваем | Жёсткий порядок сокращения объёма, code freeze за два дня |
| Люди не пользуются приложением | Пилот, обучение, простота. Это главный риск, и он не технический |
| Push не доходит (особенно iOS) | Обязательный онбординг установки + SMS для критического |
| Нет данных по участкам | Ручной ввод и работа на уровне ТИК до появления данных |
| Ограничения связи в регионе | Офлайн-режим и SMS спроектированы с первого дня |
| Утечка данных | Минимизация, роли, шифрование телефонов, аудит, второй фактор |
| Проект воспринят как внешний контроль над партией | Все данные принадлежат партии, код передаётся по итогам пилота |

## Приложение Б. Словарь

**УИК** — участковая избирательная комиссия (один участок). **ТИК** — территориальная избирательная комиссия (объединяет десятки УИК). **Куст** — группа УИК под одним координатором. **Узел** — элемент дерева мест в системе. **Фаза** — этап трёхдневного голосования. **P0–P3** — приоритеты инцидентов.
