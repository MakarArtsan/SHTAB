# ADR 0001. Область видимости штабных узлов

**Дата:** 30 августа 2026
**Статус:** принято
**Согласовано с заказчиком:** да

## Контекст

По ТЗ 4.1 дерево мест выглядит так:

```
Регион
├── Штаб региона (hq)   ← сюда привязаны dispatcher, region_head, lawyer, press
└── ТИК (tik)
    ├── Штаб ТИК (hq)
    └── УИК (uik)
```

Штабной узел — это рабочая группа при регионе или ТИК, а не место в иерархии
избирательных комиссий. В дереве он лежит **рядом** с ТИК, а не над ними.

Инвариант 2 из `CLAUDE.md` требует одной проверки доступа на всю систему:
`org_node.path <@ user_scope_path`. Если подставить в неё путь собственного узла
пользователя, то у диспетчера в поддереве окажется ровно один узел — его же штаб.
А по матрице прав ТЗ 4.3 диспетчер должен видеть весь регион. То же у юриста,
руководителя штаба и пресс-службы.

То есть буквальное прочтение ТЗ даёт штабным ролям пустую выдачу. Это пробел
в ТЗ, а не ошибка реализации.

## Рассмотренные варианты

1. **Штабной узел → путь родителя.** Область видимости выводится из узла:
   обычно это путь самого узла, а для узла типа `hq` — путь родителя.
2. **Отдельное поле `scope_node_id` в `app_user`.** У человека два узла: где
   числится и что видит.
3. **Переставить дерево:** сделать штаб родителем ТИК.

## Решение

Принят вариант 1.

```python
def scope_path(node: OrgNode) -> str:
    if node.type != NodeType.hq:
        return node.path
    parent_path, _, _ = node.path.rpartition(".")
    return parent_path
```

## Обоснование

- Область видимости остаётся **производной** от узла. Хранить её негде, значит
  нечему рассинхронизироваться и нечего подделать отдельным запросом.
- Проверка остаётся одна: `path <@ scope`. Оператор `<@` встречается ровно
  в одном файле — `api/app/core/access.py`, и это закреплено тестом
  `test_проверка_доступа_существует_в_одном_месте`.
- Вариант 2 добавляет второе поле, которое нужно защищать от самовольной смены
  (инвариант 3) и проверять при каждом создании пользователя. Это новая
  поверхность для ошибки в правах, а цена ошибки здесь — посторонний в штабе.
- Вариант 3 ломает соответствие дерева реальной избирательной структуре:
  ТИК не подчиняется партийному штабу, и в отчётах это выглядело бы неверно.

Правило работает на любом уровне: штаб ТИК видит свой ТИК, штаб региона — регион.

## Следствия

- Все штабные роли одного узла имеют одинаковую область видимости **по узлам**.
  Разница между юристом, пресс-службой и диспетчером — не в дереве, а в том,
  какие объекты внутри дерева им отдаются. Юрист видит инциденты со статусом
  «нужен юрист», пресс-служба — только агрегаты. Это фильтрация уровня объекта,
  и делается она в сервисах соответствующих модулей, а не в проверке доступа.
- Штабной узел не может быть корнем дерева: у него обязан быть родитель.
  Попытка вычислить область видимости для такого узла бросает исключение.

## Открытый долг

Роль `mobile` (выездная группа) по ТЗ 4.2 привязана к ТИК, но видеть должна
только **назначенные** УИК. Сейчас она получает всё поддерево своего ТИК —
это шире, чем в ТЗ. Согласовано как временное решение: таблица назначений
появится на этапе инцидентов, когда будет что фильтровать.
