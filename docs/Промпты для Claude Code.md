# Промпты для Claude Code

Порядок важен. Каждый промпт — отдельная сессия или отдельная задача. Не запускай следующий, пока предыдущий не проверен руками.

**Как пользоваться:** копируешь блок целиком в Claude Code, получаешь план, проверяешь план, говоришь «делай», проверяешь результат по строке «Как проверить».

**Три правила, которые экономят дни:**
1. Всегда сначала план, потом код. Если Claude Code сразу пишет код — останавливай и проси план.
2. Один промпт — одна связная функция. Большие промпты дают большие непроверяемые куски.
3. Каждый рабочий кусок — коммит. Сломалось — откатился, а не чинил три часа.

```

- docker-compose, который поднимает всё одной командой
- Makefile: up, down, migrate, seed, test, lint

Сначала покажи план файлов, потом делай.
```

**Как проверить:** `make up`, открывается `localhost:5173`, `curl localhost:8000/health` отвечает 200.

## 2. Вход и выдача учётных записей

```
Реализуй аутентификацию по ТЗ раздел 5. Самостоятельной регистрации нет.

Бэкенд:
- POST /auth/login: телефон (нормализация в +7XXXXXXXXXX) + пароль, argon2id
- JWT access 15 мин + refresh 30 дней с ротацией, привязка refresh к устройству
- POST /auth/change-password, флаг must_change_password при первом входе
- POST /admin/users — создание одного пользователя
- POST /admin/users/import — импорт CSV (фамилия;имя;телефон;роль;узел), предпросмотр с ошибками,
  генерация читаемых паролей вида «bez-lishnih-7», возврат файла для раздачи
- коды приглашений: одноразовые, с зашитой ролью и узлом, срок 72 часа
- блокировка после 5 неудачных попыток на 15 минут

Критично, проверь тестами:
- пользователь НЕ может создать роль выше своей
- пользователь НЕ может создать пользователя вне своего поддерева
- пользователь НЕ может изменить себе роль или узел
- при попытке — 403 и запись в audit_log

Фронт: экран входа (телефон + пароль), экран обязательной смены пароля, хранение токенов
не в localStorage, а в памяти + refresh в httpOnly cookie.
```

**Как проверить:** импортируй 30 строк CSV, войди наблюдателем, попробуй руками дёрнуть админский эндпоинт — должно быть 403.

## 3. Инциденты и офлайн-очередь

```
Реализуй ядро продукта — инциденты (ТЗ раздел 6.2).

Бэкенд:
- POST /incidents с идемпотентностью по client_uuid (уникальный индекс)
- категории и приоритеты из справочника в /data/categories.json
- GET /incidents с фильтрами по узлу, статусу, приоритету, пагинация
- PATCH /incidents/{id} — смена статуса и владельца, с проверкой прав
- POST /incidents/{id}/evidence — presigned upload в S3, сохранение sha256, времени устройства и сервера
- incident_event — таймлайн всех изменений

Фронт (мобильный приоритет, ширина 360 px):
- экран «Пульт»: 4 крупные кнопки (Всё в порядке / Есть вопрос / Нарушение / SOS)
- создание инцидента: категория плиткой → описание (с голосовым вводом через Web Speech API,
  если доступен) → фото → отправить. Не больше 4 нажатий.
- офлайн-очередь на Dexie: событие пишется локально, показывается со статусом «ожидает отправки»,
  отправляется при появлении сети
- счётчик неотправленных всегда виден на главном экране
- сжатие фото до 1600 px перед отправкой

Экран «нет соединения» показывать нельзя. Всё работает офлайн.
```

**Как проверить:** выключи сеть в девтулзах, создай три инцидента с фото, включи сеть — все три ушли, дублей нет.

## 5. Чат-система по иерархии

```
Реализуй чаты (ТЗ раздел 6.5). Общего чата на всех НЕТ.

Каналы создаются автоматически: uik:{id}, tik:{id}, region:{id}, incident:{id}, announce:{node}.
Правила доступа:
- наблюдатель видит только канал своего УИК и объявления
- координатор — каналы своих УИК и канал своего ТИК
- личные сообщения только по вертикали: наблюдатель ↔ свой координатор
- писать в чужой УИК нельзя, канал даже не должен быть виден

Функции: текст, фото, голосовые сообщения, цитирование, пометка «срочно» (звук у получателей),
кнопка «сделать инцидентом», непрочитанные, поиск по истории.
Удалять сообщения может координатор и выше, удаление пишется в audit_log с сохранением текста.

Техника: WebSocket через Redis pub/sub, при обрыве — long-poll раз в 10 секунд,
история страницами, отправка идемпотентна по client_uuid, офлайн-черновики в общей очереди.

Тесты обязательны: наблюдатель А не может прочитать и не видит канал УИК наблюдателя Б.
```

**Как проверить:** два браузера, два наблюдателя из разных УИК — не видят друг друга. Координатор видит обоих.

## 7. Уведомления и рассылки

```
Реализуй центр уведомлений (ТЗ раздел 6.6).

Типы: broadcast, targeted, personal, system. Приоритеты: info, important, critical.
- панель рассылки: выбор аудитории (узел + роли + фильтр «только без связи»),
  предпросмотр числа получателей, приоритет, шаблоны
- доставка: внутри приложения (WebSocket) → Web Push (VAPID) → SMS для critical
- critical требует подтверждения прочтения; если через 10 минут нет ack — SMS,
  ещё через 10 — задача координатору «позвонить»
- notification_receipt: доставлено / прочитано / подтверждено, по каждому получателю
- лимит частоты рассылок, чтобы люди не начали их игнорировать
- рассылка требует подтверждения и пишется в audit_log

SMS-провайдер за интерфейсом в services/providers/sms.py, с заглушкой для локальной разработки
(пишет в лог вместо отправки).

Экран у пользователя: список уведомлений, непрочитанные, кнопка «Подтверждаю» для critical.
```

**Как проверить:** отправь critical на 5 тестовых пользователей, подтверди у двоих — у трёх должна уйти SMS-заглушка в лог.

## 9. ИИ-помощник (RAG)

```
Реализуй помощника по избирательному законодательству (ТЗ раздел 6.8).

Конвейер: вопрос → гибридный поиск по kb_chunk (полнотекст + вектор, pgvector)
→ топ-6 фрагментов → если максимальная релевантность ниже порога, вернуть честное «не знаю»
с кнопкой «позвать юриста» → иначе генерация строго по фрагментам
→ пост-проверка: если в ответе нет ссылки на источник из выдачи, ответ НЕ показывать, эскалировать.

Провайдер модели за интерфейсом services/providers/llm.py, реализация для GigaChat,
заглушка для тестов. Эмбеддинги — локальная многоязычная модель на CPU.

Формат ответа фиксированный:
1) короткий ответ 1–2 предложения человеческим языком (60–90 слов максимум)
2) «Что сделать сейчас» — 2–4 пункта
3) «Основание» — свёрнуто, со ссылкой на статью базы знаний
4) кнопки: Помогло / Позвать юриста / Оформить жалобу

Системный промпт: спокойный коллега, а не юрист на трибуне. Запрещённые обороты:
«в соответствии с положениями», «надлежит», «вышеуказанный». Не выдумывать номера статей.
Не давать оценок законности выборов. Не подталкивать к конфликту с комиссией.

Сделай также скрипт evals/run.py: прогоняет набор вопросов из evals/questions.yaml
и считает метрики — доля верных, доля выдуманных ссылок (должна быть 0),
доля честных «не знаю» на вопросах вне корпуса.

Топ-100 карточек кэшируются офлайн, при отсутствии сети помощник отвечает по кэшу с пометкой.
```

**Как проверить:** задай 10 вопросов, включая один заведомо вне корпуса («можно ли пронести собаку на участок») — должно быть честное «не знаю».

## 12. Трёхдневка: фазы, сейф-пакеты, протокол

```
Реализуй специфику трёхдневного голосования (ТЗ разделы 6.3 и 6.4).

Фазы: подготовка, открытие, день, закрытие дня, открытие следующего дня, подсчёт, протокол.
Текущая фаза считается автоматически по дате, времени и часовому поясу узла.
Для каждой фазы — чек-лист с тумблерами «да / нет / спорно».
«Нет» и «спорно» автоматически создают инцидент с предзаполненным описанием.

Сейф-пакеты: вечером — ввод номеров пломб (можно несколько) + фото + кто присутствовал.
Утром — система показывает вчерашние номера и просит подтвердить.
Расхождение → инцидент P0 + предзаполненный проект жалобы.

Явка: ввод в контрольные часы с напоминанием, график по участку и кусту.

Протокол: фото → OCR чисел → обязательная ручная проверка человеком →
проверка контрольных соотношений из конфига /data/protocol_checks.json →
предупреждение о несходящихся строках ДО подписания. Флаг «заверенная копия получена».

Контрольные соотношения — в конфиге, не в коде.
```

**Как проверить:** введи вечером три номера пломб, утром измени один — должен появиться инцидент P0.

## 13. Нагрузка, мониторинг, бэкапы

```
Подготовь систему к боевому дню.

- нагрузочный тест (locust или k6): 3000 одновременных пользователей,
  50 запросов/сек, 500 сообщений в минуту. Найди и почини узкие места.
- индексы под реальные запросы, проверь планы через EXPLAIN ANALYZE
- rate limiting на все публичные эндпоинты
- Sentry или GlitchTip для ошибок, Uptime Kuma для доступности
- бэкап Postgres каждый час + проверка восстановления, бэкап S3 ежедневно
- health-эндпоинт с проверкой БД, Redis, S3, очередей
- страница /status для администратора: длина очередей, задержки, ошибки за час
- документ docs/runbook.md: что делать, если упала БД, если растёт очередь,
  если не уходят SMS, если WebSocket отваливается. Пиши для человека в 4 утра.
```

**Как проверить:** прогони нагрузочный тест и восстанови базу из бэкапа на чистом окружении.

## Промпты на каждый день (короткие)

**Начало дня:**
```
Прочитай CLAUDE.md и docs/ТЗ.md. Покажи текущее состояние: что готово, что нет,
что сломано. Предложи 3 задачи на сегодня по приоритету, с оценкой времени.
```

**Разбор бага:**
```
Баг: [что сделал] → [что ожидал] → [что получилось]. Логи: [вставить].
Не чини сразу. Сначала найди причину и объясни её. Потом предложи минимальное исправление
и скажи, что ещё могло сломаться по той же причине.
```

**Перед code freeze:**
```
Пройди по критическим сценариям и проверь каждый:
1) вход наблюдателя, 2) создание инцидента офлайн и синхронизация,
3) появление инцидента у диспетчера, 4) чат УИК, 5) critical-рассылка с подтверждением,
6) база знаний офлайн, 7) сейф-пакеты с расхождением.
Найди, где не хватает обработки ошибок, и почини только то, что реально может сломаться в бою.
Ничего не рефактори.
```

**Ревью безопасности:**
